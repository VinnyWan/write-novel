## Context

当前 `write-novel-setup` Phase 1.6 调用 story-architect agent 生成 `设定/世界观.md` 和 `设定/题材定位.md`，agent 产出后直接写入文件，用户无介入窗口。这是初始化阶段的首次世界观构建，用户尚未建立明确偏好，全自动生成的设定与用户隐性创作意图偏差概率较高。

约束：
- 项目配置已在 Phase 1.5 收集完毕（题材、风格、目标字数），可作为 agent prompt 参数
- story-architect agent 是独立子进程，需要明确指令：生成初稿 vs 写入文件
- 交互流程在 setup skill 的主线程执行，不能委托给 agent

## Goals / Non-Goals

**Goals:**
- 世界观初稿生成后、落盘前，向用户展示并收集确认/修改反馈
- 世界观六大板块和题材定位三大板块均可独立确认
- 支持逐项精细确认和批量全部确认两种模式
- 确认后的内容统一写入文件，附带 frontmatter 校验（与现有 Gate 1.6.4 衔接）

**Non-Goals:**
- 不改变 story-architect agent 的生成逻辑本身
- 不修改 `.story-config.json` 的配置项
- 不改变 Phase 1.6 之后其他 Phase 的流程
- 不涉及已存在 `设定/世界观.md` 时的重跑逻辑（Phase 1.6.2 的重跑检测保持不变）

## Decisions

### D1：Agent 调用一拆为二

当前：agent 一次调用完成生成 + 写入。
改为：agent 只产出初稿（返回文本），主线程缓存初稿，逐板块展示交互，最后主线程写入文件。

**Why**: 交互确认必须在主线程执行（AskUserQuestion 是主线程工具），agent 子进程无法与用户交互。

**Alternatives considered**:
- 让 agent 逐板块问 → 不可行，子进程无法调用 AskUserQuestion
- 写入临时文件后主线程读回展示 → 增加文件 I/O，不如直接内存传递

### D2：交互确认采用分步展示

初稿生成后，分两轮展示：
- **第一轮**（世界观六大板块）：时代背景 → 地理环境 → 势力格局 → 力量体系 → 社会结构，每项单选「确认/修改」
- **第二轮**（题材定位三大板块）：题材类型 → 核心梗三分法 → 对标作品，每项单选「确认/修改」

每轮支持「全部确认」快速跳过。

**Why**: 逐板块确认粒度适中——不会因逐行确认过于繁琐，也不会因整篇确认失去细节控制。分组切分世界观和题材定位也符合用户的认知切换。

### D3：修改模式让用户输入修正文本

选择「修改」时弹出文本输入框，用户输入修正后的完整段落。不采用逐句/逐字段编辑——保持自然语言描述的一致性是用户的判断，不应由工具拆分。

**Why**: 世界观描述是自然语言长文本，拆分字段编辑会破坏连贯性。完整段落替换保持语义完整性。

### D4：Phase 1.6.4 Gate 校验前置

确认完成后、写入文件时，依然执行 Phase 1.6.4 的 frontmatter 和关键段落校验。用户修改后如果缺少必要字段，提示补全后再写入。

**Why**: 用户修改可能误删 frontmatter 标记字段，需要保持结构性校验。

## Risks / Trade-offs

- **交互轮次增加**：长篇项目原先 Phase 1.6 约 10 秒自动完成，现在需要用户参与约 2-4 轮交互。→ Mitigation：提供「全部确认」快捷选项，接受默认生成的用户可一键跳过
- **上下文膨胀**：世界观初稿全文缓存在主线程会增加上下文占用。→ Mitigation：仅缓存初稿文本，不附加上下文分析
- **用户跳过导致内容为空**：用户理论上可对所有板块选「跳过」→ Mitigation：Phase 1.6.4 Gate 拒绝空字段，必须至少有一项确认或修改后的内容
