# 标准化作者报告模板

## 原则

- **作者只看到自然语言，不看到内部结构**：JSON、traceback、原始 agent 输出一律不暴露
- **状态可操作**：作者读完报告就知道进度、问题和下一步要做什么
- **命令可复制**：下一步命令用代码块呈现，可直接复制执行

## 三段式结构

```markdown
## 📋 完成状态

**状态：已完成 | 部分完成 | 需要你处理 | 未完成**

### 已生成文件
- `文件路径1` — 说明
- `文件路径2` — 说明

{如果部分完成，列出已完成和未完成的对比}

---

## ⚠️ 问题

### 自动处理（无需你介入）
- {问题描述} → 已自动修复：{修复动作}

### 建议检查（你可选查看）
- {问题描述} — 影响范围：{简要说明}

### 必须处理（阻塞后续工作）
- {问题描述} — 修复方向：{建议}

{如果无问题，写"无问题"}

---

## 🔜 下一步

```bash
/write-novel-long-write 43
```

{或列出 2-3 个可选下一步命令}
```

## 状态分类标准

| 状态 | 含义 | 示例 |
|------|------|------|
| **已完成** | 所有步骤成功完成，无阻塞问题 | 章节写作+审查+提交全通过 |
| **部分完成** | 部分步骤成功，有非阻塞性问题 | 写了正文但审查发现 S3 问题 |
| **需要你处理** | 存在阻塞性问题，需作者决策 | 审查发现角色设定矛盾 |
| **未完成** | 操作无法开始或被中止 | 缺少细纲文件，无法写作 |

## 问题严重度映射

| 内部级别 | 报告分组 | 说明 |
|---------|---------|------|
| blocking / S1 / critical | **必须处理** | 阻塞后续工作，需作者决策 |
| S2 / high | **建议检查** | 建议本轮修复 |
| S3 / medium / low | **建议检查** | 可排期修复 |
| S4 / info | 不单独列出 | 或归入"建议检查"底部 |
| auto-fixed | **自动处理** | 已自动修复，无需作者介入 |

## 使用规范

1. 所有 skill 的最终用户可见输出必须使用此模板
2. 内部 JSON、traceback 仅在诊断模式（用户主动要求）下可暴露
3. 下一步命令必须有效且可执行，使用项目当前上下文
4. 文件路径使用相对于项目根目录的路径
5. 中文输出遵循《中文文案排版指北》

## 错误文案与术语引用

报告中的错误描述和工程术语 SHALL 统一引用结构化资产，不得硬编码：

- **错误目录** `references/shared/author_error_catalog.json`：遇到已知失败模式（写前/写后自检未过、伏笔逾期、字数不达标、合约不合规、章节提交被拒、投影失败等）时，按 `code` 查得作者可读的标题/原因/影响/下一步动作，填入「⚠️ 问题」对应分组。`auto_handle=true` 的问题归入「自动处理」，`must_handle` 归入「必须处理」，`should_handle` 归入「建议检查」。
- **作者术语表** `references/shared/author_glossary.json`：面向作者的输出若需使用工程术语（frontmatter、合约、prewrite-gate、CHAPTER_COMMIT、run-ledger、投影、快照等），SHALL 先经术语表映射为作者可读中文名。
- 新增失败模式时，先在错误目录登记 `code` 与可读文案，再在流程中引用。
